# Модель угроз: аутентификация, хранение ключей и стойкость шифрования базы данных

> **Статус документа:** Архитектурная спецификация и честный анализ стойкости  
> **Область анализа:** Графический ключ (Pattern), PIN-код, аппаратный Android Keystore, SQLCipher, Argon2id, PBKDF2  
> **Версия кодовой базы:** ADA Core 0.5.0, Android App 0.5.0, Windows Desktop 0.5.0  

---

## 1. Введение и цели анализа

ADA Messenger проектировался для работы без централизованных серверов и учетных записей, привязанных к телефонным номерам. Для защиты локальных данных пользователя на устройстве применяется шифрование базы данных SQLCipher (AES-256-CBC) и двухуровневое хранилище ключей.

Цель данного документа — **прозрачно и строго (без маркетинговых допущений)** зафиксировать:
1. Как математически и физически выводятся ключи шифрования.
2. Чем режим «только графический паттерн» отличается от режима «паттерн + PIN-код».
3. Как привязка к аппаратному хранилищу (Android Keystore / TEE) влияет на стойкость при физическом изъятии устройства.
4. Каковы реальные ограничения криптографических механизмов и человеческого фактора.

## 2. Иерархия деривации ключей (Key Derivation Architecture)

```
                     ┌──────────────────────────────────────────────┐
                     │   Графический ключ (5 цветов × 16 ячеек)    │
                     └──────────────────────┬───────────────────────┘
                                            │ canonical flat bytes [32 B]
                                            ▼
                     ┌──────────────────────────────────────────────┐
                     │          Argon2id (t=3, m=64 MiB, p=1)       │
                     │          + ada_identity.salt [32 B]          │
                     └──────────────────────┬───────────────────────┘
                                            │ master_seed [32 B]
                                            ▼
                                ┌───────────────────────┐
                                │      HKDF-SHA256      │
                                └───────────┬───────────┘
                 ┌──────────────────────────┼──────────────────────────┐
                 ▼                          ▼                          ▼
     "ada/signing-key/v1"           "ada/dh-key/v2"            "ada/db-enc-key/v1"
                 │                          │                          │
                 ▼                          ▼                          ▼
        Ed25519 Signing Key         X25519 Identity DH          SQLCipher DB Key
          (Peer ID node)             (X3DH / PQXDH)            (AES-256-CBC для БД)
                                                                       │
                                                                       ▼
                                                             "ada/ratchet-enc/v1"
                                                                       │
                                                                       ▼
                                                               XChaCha20-Poly1305
                                                              (Второй слой для ratchet)
```

1. **Первичный ввод (Master Secret):**
   * Пользователь расставляет 16 кубиков по сетке 8×8 (64 ячейки), используя до 5 цветов.
   * Координаты и цвета сортируются по индексу ячейки в канонический 32-байтный массив `[idx0, col0, idx1, col1, ...]` (`PatternKey`).
2. **Стойкая функция растяжения (Argon2id):**
   * Паттерн подается в **Argon2id** (версия 0x13, $t=3$ итерации, $m=64$ МиБ оперативной памяти, $p=1$ поток).
   * Соль: 32 случайных байта из системного генератора случайных чисел (`ada_identity.salt`), генерируемые один раз при первой регистрации и сохраняемые открыто в каталоге данных приложения.
   * Результат: 32-байтный псевдослучайный `master_seed`.
3. **Вывод ключей компонентов (HKDF-SHA256):**
   * `ada/signing-key/v1` → сид для долговременного Ed25519 ключа идентификации (публичный ключ = `peer_id`).
   * `ada/dh-key/v2` → долговременный приватный ключ X25519 для установления сквозных сессий (X3DH / PQXDH).
   * `ada/db-enc-key/v1` → 32-байтный симметричный мастер-ключ локальной базы данных **SQLCipher**.
   * `ada/ratchet-enc/v1` → дополнительный ключ для XChaCha20-Poly1305 шифрования состояний сессий (Double Ratchet) внутри таблицы `ratchet_enc`.

## 3. Анализ энтропии паттерна и человеческий фактор

### Теоретическая оценка
Количество способов выбрать 16 уникальных ячеек из 64 на сетке 8×8 с возможностью раскрасить каждую ячейку в один из 5 цветов:
$$N = \binom{64}{16} \times 5^{16} \approx 4.885 \times 10^{14} \times 1.526 \times 10^{11} \approx 7.45 \times 10^{25}$$
Теоретическая энтропия:
$$\log_2(7.45 \times 10^{25}) \approx 85.9 \text{ бит}$$

При затратах памяти 64 МиБ на одну попытку в Argon2id перебор случайного 86-битного пространства невозможен даже с применением суперкомпьютеров и специализированных ASIC.

### Реальность человеческого фактора (Human Bias)
> ⚠️ **Важное ограничение безопасности:**
> Реальная стойкость пароля всегда определяется **практическим распределением выбора пользователя**, а не теоретической комбинаторикой.

1. **Геометрические паттерны:** Люди склонны рисовать узнаваемые фигуры: кресты, квадраты, диагонали, буквы, углы сетки.
2. **Цветовая асимметрия:** Пользователи часто красят все 16 кубиков в один любимый цвет или чередуют всего два цвета, сокращая пространство цветов с $5^{16}$ до $1$ или $2^{16}$.
3. **Защита от тривиальных узоров (3 цвета):** Система принудительно требует использования **как минимум 3 различных цветов из 5** (`MIN_REGISTRATION_DISTINCT_COLORS = 3`). Узоры из 1 или 2 цветов отклоняются интерфейсом с предупреждением и блокируются ядром (`PatternKey::validate_registration`).

4. **Вывод:** Если пользователь выбрал простой рисунок (например, две крайние горизонтальные линии одного цвета), злоумышленник с тематическим словарём геометрических шаблонов сможет перебрать такой паттерн значительно быстрее полного перебора.

## 4. Графический паттерн и непрошибаемый протокольный модуль PIN (ADPV)


В приложении предусмотрено два режима работы:

### Режим А: Чистый паттерн (Zero-Secret-At-Rest)
* **Как хранится секрет:** Секрет паттерна (`patternCells`) **никогда не сохраняется на постоянном носителе (флеш-памяти)**.
* **Жизненный цикл ключей:** При выходе из приложения или блокировке все производные ключи в памяти обнуляются (`zeroize::ZeroizeOnDrop`).
* **Поведение при физическом изъятии (BFU — Before First Unlock):**
  * Если устройство выключено или приложение выгружено из памяти, на диске остаются только:
    1. `ada.db` — зашифрованная база данных SQLCipher.
    2. `ada_identity.salt` — 32-байтная соль.
  * Для расшифровки базы злоумышленник обязан перебирать полный графический паттерн через Argon2id.
  * **Стойкость:** Максимальная, определяется сложностью выбранного пользователем паттерна.

---

### Режим Б: Быстрый доступ по PIN-коду (ADPV — ADA Protocol Vault)
Для повседневного удобства пользователь может активировать быстрый вход по короткому PIN-коду (от 4 символов).

#### Архитектурное требование и привязка к протоколу:
Защита PIN вынесена в отдельный изолированный криптографический модуль ядра `ada-core::crypto::pin_vault` (бинарный конверт `ADPV` версии 1).  
**Чтобы вскрыть PIN, злоумышленник обязан предварительно расшифровать сам протокол устройства**, где лежит 256-битный протокольный якорь (`protocol_anchor`).

#### Механизм реализации:
1. На устройстве генерируется и сохраняется под аппаратной защитой 256-битный протокольный секрет (`protocol_anchor`).
2. Введенный пользователем PIN растягивается через memory-hard алгоритм **Argon2id** (64 MiB RAM, 3 итерации, 1 поток, 16-байтная случайная соль `salt`).
3. 256-битный `protocol_anchor` и 256-битный растянутый PIN объединяются в 512-битный IKM:
   $$\text{IKM} = \text{protocol\_anchor} \,\|\, \text{Argon2id}(\text{PIN}, \text{salt})$$
4. Через **HKDF-SHA256** с солью `salt` и контекстной меткой `b"ada/pin-vault-protocol/v1"` выводится 256-битный ключ хранилища `vault_key`.
5. 32-байтный массив `patternCells` зашифровывается алгоритмом **AES-256-GCM** с 96-битным случайным `nonce` и AAD `[b"ADPV", 0x01, salt]`.

```text
Ввод PIN-кода (4+ цифр)                Протокольный якорь устройства
        │                                      │ (256 бит энтропии протокола)
        ▼                                      │
Argon2id (64 MiB, t=3) ────────┐               │
                               ▼               ▼
                        IKM = [ protocol_anchor || pin_stretched ] (512 бит)
                                       │
                                       ▼
                 HKDF-SHA256 (salt, info="ada/pin-vault-protocol/v1")
                                       │
                                       ▼
                       vault_key (256 бит AES-256-GCM)
                                       │
                                       ▼
                AES-256-GCM расшифровка контейнера ADPV (81 байт)
                                       │
                                       ▼
                            Исходный patternCells (32 B)
                                       │
                                       ▼
                            Argon2id (t=3, m=64 MiB)
                                       │
                                       ▼
                         Ключ базы данных SQLCipher (ada.db)
```

#### Векторы атак и гарантированная стойкость:

| Условие атаки | Что защищает базу? | Фактическая стойкость базы |
| :--- | :--- | :--- |
| **Режим только Паттерна** (PIN выключен) | Argon2id от 16 кубиков ($\ge 3$ цветов) | **86 бит теоретически** |
| **PIN включен, обычный запуск на Android** | Android Keystore + Argon2id + ADPV Vault | **Аппаратная защита TEE/StrongBox** |
| **PIN включен, физический дамп флеш-памяти** | ADPV Protocol Vault + 256-битный протокольный якорь | **$2^{256}$ комбинаций!** Оффлайн-перебор PIN невозможен без расшифровки протокольного ключа |
| **PIN включен на Desktop** | ADPV Protocol Vault + привязка к протоколу устройства | **$2^{256}$ комбинаций** против изоляции PIN |

> 🔒 **Ключевой технический вывод:**  
> Благодаря связыванию PIN с 256-битным протокольным секретом устройства в модуле `ADPV`, изолированный брутфорс PIN-кода по дампу памяти не дает злоумышленнику ключа шифрования: пространство поиска остается равным $2^{256}$. Для вскрытия PIN необходимо полностью скомпрометировать криптографический протокол устройства.

## 5. Аварийные механизмы (Kill PIN и Clean PIN)

1. **Kill PIN (Код самоуничтожения):**
   * Пользователь может настроить отдельный PIN-код для экстренного стирания.
   * При вводе Kill PIN на экране разблокировки приложение немедленно выполняет:
     - Очистку всех записей в памяти (`zeroize`).
     - Удаление файла базы данных `ada.db` и вспомогательных файлов SQLite WAL/SHM.
     - Удаление файла соли `ada_identity.salt`.
     - Очистку всех настроек `EncryptedSharedPreferences`.
   * **Ограничение flash-памяти:** На мобильных устройствах (NAND Flash / UFS) удаление файла через ОС выполняет операцию `unlink`. Физические секторы памяти не перезаписываются мгновенно из-за работы контроллера износа (Wear Leveling) и отложенного выполнения команды TRIM.
2. **Clean PIN (Режим ложного интерфейса / Decoy):**
   * При вводе Clean PIN открывается чистый, пустой интерфейс мессенджера без истории и контактов, создавая видимость нового приложения.

## 7. Рекомендации по безопасности для пользователей

1. **Если ваша модель угроз включает физическое изъятие устройства экспертами:**
   * **НЕ ВКЛЮЧАЙТЕ разблокировку по PIN-коду.**
   * Используйте только графический паттерн. В этом случае на устройстве физически не остаётся ключа для расшифровки базы данных.
2. **При выборе графического паттерна:**
   * Избегайте симметрий, прямых линий и одноцветных блоков.
   * Используйте все 5 доступных цветов и распределяйте кубики максимально хаотично по всей сетке 8×8.
3. **При использовании десктопной версии (Windows):**
   * Помните, что в настольной ОС отсутствует аналог аппаратного модуля Android Keystore с физическим ограничением частоты подбора. Защита файлов приложения зависит от шифрования системного диска (BitLocker).

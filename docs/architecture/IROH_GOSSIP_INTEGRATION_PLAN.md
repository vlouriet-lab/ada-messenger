# План интеграции iroh-gossip в ADA Messenger

## 1. Концепция и цели

### 1.1. Проблема текущей архитектуры
В текущей реализации ADA все групповые взаимодействия работают по схеме **Full Mesh («каждый с каждым»)**:
* **Текстовые сообщения и файлы:** отправитель выполняет $O(N)$ независимых сетевых отправок каждому участнику группы. При увеличении группы свыше 16 человек это перегружает мобильный канал и батарею.
* **Групповые звонки:** каждый участник устанавливает прямое медиа-соединение со всеми остальными. При $N$ участниках общее количество медиапотоков составляет $N(N - 1)$. При $N = 16$ это 240 потоков, что физически невозможно на мобильных устройствах.

### 1.2. Решение: разделение Control Plane и Data Plane
Мы разделяем архитектуру групповых коммуникаций на два специализированных контура:

1. **Gossip Control Plane (`iroh-gossip`):**
   * **Групповые чаты:** рассылка E2E-зашифрованных сообщений (`SenderKeyMessage`), ротация ключей (`SenderKeyDistribution`), метаданные файлов и реакции. Масштабируемость: **от 16 до 100+ участников** без нагрузки на центральные узлы.
   * **Сигналинг групповых звонков:** объявление звонка (`CallSessionAnnouncement`), обмен статусами участников (joined, left, mute, camera), обмен SDP-офферами и ICE-кандидатами через топик группы.
2. **Direct Media Plane (Full-Mesh WebRTC / Iroh QUIC Streams):**
   * Передача живых аудио- (Opus) и видеопотоков (VP8/H.264) **напрямую между пирами**.
   * Никакого gossip для медиапотоков (сохраняется минимальная задержка $< 150$ мс без джиттера от промежуточных хопов).
   * **Жёсткий лимит участников звонка:** **ровно до 6 человек** (в группе может быть 100 человек, но в голосовом/видеозвонке одновременно могут находиться максимум 6 участников).

```
                      ┌───────────────────────────────────────────────┐
                      │             GROUP CHAT (N ≤ 100+)             │
                      └───────────────────────┬───────────────────────┘
                                              │
                    ┌─────────────────────────┴─────────────────────────┐
                    ▼                                                   ▼
       ┌────────────────────────┐                          ┌────────────────────────┐
       │  GOSSIP CONTROL PLANE  │                          │   DIRECT MEDIA PLANE   │
       │     (iroh-gossip)      │                          │ (Full-Mesh WebRTC/QUIC)│
       ├────────────────────────┤                          ├────────────────────────┤
       │ • Текстовые сообщения   │                          │ • Аудиопотоки (Opus)   │
       │ • Ротация Sender Keys  │                          │ • Видеопотоки (VP8/H264│
       │ • Метаданные вложений  │                          │ • Прямой P2P RTT <150ms│
       │ • Сигналинг звонков    │                          │ • ЛИМИТ: ровно ≤ 6 чел │
       │ • Топология: PlumTree  │                          │ • Сетка: до 2×3 в UI   │
       └────────────────────────┘                          └────────────────────────┘
```

## 2. Архитектура Gossip Control Plane (`ada-core`)

### 2.1. Идентификация и скрытие метаданных (Blind Topics)
Чтобы узлы глобальной сети Iroh не знали, какая группа общается в топике:
$$\text{TopicId} = \text{BLAKE3}(\text{group\_id} \parallel \text{"ada-gossip-v1"})$$
* Открытый `group_id` нигде не светится в сетевом заголовке топика.
* Доступ к топику имеют только те, кто знает идентификатор группы.

### 2.2. Защита от спама и атак Сивиллы (Validator Callback)
`iroh-gossip` предоставляет интерфейс валидации сообщений до их ретрансляции по дереву PlumTree.
Каждое сообщение заворачивается в конверт:
```rust
pub struct GossipEnvelope {
    pub sender_peer_id: [u8; 32],
    pub signature: [u8; 64], // Ed25519 подпись тела сообщения
    pub sequence: u64,
    pub payload: GossipPayload,
}

pub enum GossipPayload {
    ChatMessage(SenderKeyMessage),
    SenderKeyRotation(SenderKeyDistribution),
    CallSignaling(GroupCallSignal),
    MembershipEvent(GroupMembershipEvent),
}
```
**Правило валидатора:** узел проверяет, что `sender_peer_id` входит в локальный список участников группы и подпись верна. Невалидные сообщения отбрасываются и не пересылаются дальше.

## 3. Сигналинг звонков и ограничение в 6 участников

### 3.1. Протокол сигналинга через Gossip
Вместо попарной рассылки WebRTC-офферов через pairwise E2E-каналы, события звонка транслируются в Gossip-топик группы:
1. `CallStarted { call_id, initiator_peer_id, has_video }`
2. `JoinRequest { call_id, peer_id }`
3. `JoinAccepted { call_id, peer_id, active_participants }` — отклоняется, если участников уже 6.
4. `SdpExchange { call_id, from_peer, to_peer, sdp }`
5. `IceCandidate { call_id, from_peer, to_peer, candidate }`
6. `CallStateUpdate { call_id, peer_id, is_muted, is_camera_off, is_screen_sharing }`
7. `ParticipantLeft { call_id, peer_id }`

### 3.2. Автоматическое соблюдение лимита $\le 6$
* В момент когда в сессии звонка регистрируется 6 участников:
  - Топик рассылает состояние `CallCapacityFull(true)`.
  - У всех остальных участников группы в UI кнопка «Присоединиться к звонку» блокируется с пояснением: *«В звонке максимум участников (6/6)»*.
  - Если участник выходит из звонка, освобождается слот, и кнопка снова становится активной.

## 5. Ожидаемые метрики и результаты
1. **Трафик при отправке в чат:** снижается с $O(N)$ до константного $O(1)$ на узел-отправитель (рассылка только 3–4 соседям).
2. **Лимит участников чата:** увеличивается с 16 до **100+ участников**.
3. **Надёжность звонков:** устраняются сбои сигналинга при старте звонка (все участники узнают о звонке моментально через единый топик).
4. **Стабильность видеозвонков:** ограничение в **6 участников** гарантирует, что ни одно устройство не превысит допустимый битрейт и лимит аппаратных декодеров (максимум 5 входящих потоков на участника).
